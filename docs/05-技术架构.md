# 05 · 多端技术架构

> 平台策略：**保留已交付 Web H5 M1 → iOS-first（当前最高优先级）→ 微信小程序 / Android 后续复用**。2026-07-29 经专项评审批准，iOS 进入实施阶段。

> 2026-08-10 决策：当前交付目标为**个人本地版**。SQLite 是唯一业务事实来源，先完成备份/恢复、本地提醒与真机自用；图中的服务端、账号、同步、远程推送与在线 AI 保留为 v1.1 目标，不是当前 v1 依赖。

## 1. 多端复用策略：共享大脑，各自穿衣

多端最大的坑是"想一套代码跑所有端"，结果每个端都是二等公民。我们的策略是：**业务逻辑 100% 共享，UI 每端原生手感**。

```
┌─────────────────────────────────────────────────────┐
│                    各端 UI 层（不共享）                 │
│  Web/H5(React)   iOS(Expo RN)   小程序/Android(后续)  │
├─────────────────────────────────────────────────────┤
│              共享层（纯 TypeScript，平台无关）           │
│  @tickcap/core     领域模型、时间推断、统计计算、校验     │
│  @tickcap/api      类型安全的 API 客户端（自动生成）      │
│  @tickcap/tokens   设计令牌（颜色/字号/间距/动效参数）     │
├─────────────────────────────────────────────────────┤
│                     服务端（唯一后端）                  │
│   REST API · 账号 · 数据存储 · AI 代理 · 提醒调度        │
└─────────────────────────────────────────────────────┘
```

**为什么这样切**：
- `core` 装的是产品的灵魂逻辑：时间自动推断（新胶囊开始 = 上颗结束）、空隙计算、streak 计算、统计聚合、复盘数据打包。这些逻辑写一遍，三端行为永远一致。
- iOS 选 **Expo React Native + 必要 Swift 扩展**：直接复用 `core`/`tokens`/`api`，主应用保持 React/TypeScript；WidgetKit、App Intents 等系统能力在确需时使用受控原生扩展。
- 小程序后续选 **Taro（React 语法）**；Android 在 iOS v1 稳定后复用 Expo RN，但必须单独完成平台适配与验收。
- 设计令牌（tokens）以 JSON 为源，构建时生成 Web 的 CSS 变量、小程序的 wxss 变量、RN 的 JS 常量——**三端视觉出自同一份定义，改一处全端生效**。

## 3. 技术选型

| 层 | 选型 | 理由 |
|----|------|------|
| Web 框架 | **Next.js（App Router）+ TypeScript** | 一个框架同时承载：应用本体（H5）、官网落地页（SEO）、**分享页**（年报/周报卡片被分享出去时需要服务端渲染出漂亮的预览图和落地页——这是增长引擎的技术前提） |
| UI | **Tailwind CSS v4** + 自研组件 | 由 tokens 驱动；不引入重型组件库——本产品 90% 的界面是自定义的时间轴与胶囊，组件库帮不上忙反而拖手感 |
| 动效 | **Motion (Framer Motion)** | 封存动画、胶囊入轴动画、"现在线"呼吸感是产品体验的一部分，需要专业动效库 |
| 状态/数据 | **Zustand + TanStack Query** | 轻量、和 RN 通用（未来 App 端直接复用数据层写法） |
| PWA | next-pwa / Serwist | 可安装到主屏、离线打开今日页、Web Push 的前提 |
| 服务端 | **Node.js + Hono + TypeScript** | 轻、快、类型安全，单人可维护；OpenAPI 输出给 `@tickcap/api` 生成客户端 |
| 数据库 | **PostgreSQL + Drizzle ORM** | 关系型是正解（时间区间查询、统计聚合多）；Drizzle 轻量类型安全 |
| 缓存/队列 | 先不引入 | Redis 等到提醒调度和 AI 队列有真实压力再上，MVP 用 Postgres 够 |
| AI | **服务端统一代理**，供应商适配器模式 | 前端永不直连大模型。适配 DeepSeek / 通义 / 豆包（均已备案，利于国内合规），可按成本随时切换；日复盘用中档模型，长报告用高档模型；SSE 流式输出到前端（复盘逐字生成的体验好且显得快） |
| 部署 | 国内云（阿里云/腾讯云）Docker 单机起步 | 目标用户在国内，域名需 ICP 备案（**尽早启动，流程约 2–4 周**）；前后端同域部署 |
| 埋点 | 自建 events 表 + 后台看板（或自托管 PostHog/Umami） | 封存率、胶囊数、复盘编辑率是生死指标，第一天就要能看 |

### 3.1 iOS 客户端基线

| 层 | 选型 | 约束 |
|----|------|------|
| 应用框架 | Expo React Native + Expo Router + TypeScript | 使用 Development Build/CNG；Expo Go 不作为生产验证载体 |
| 最低系统 | iOS 18.0 | 首要真机为 iPhone 14 / iOS 18.7.1 |
| 本地数据 | `expo-sqlite` | SQLite 是本地事实来源；业务写入与 outbox 同事务 |
| 视图状态 | Zustand | 只保存会话/UI 状态，不把完整业务库复制进内存持久化 |
| 服务端数据 | `@tickcap/api` + 同步引擎（v1.1） | 个人本地版不联网；未来 UI 不直接散写 `fetch` |
| 密钥 | Keychain（Expo SecureStore） | token 禁止放 AsyncStorage/SQLite/日志 |
| 通知 | Expo Notifications + 必要原生模块 | G1 必须验证后台/杀进程/锁屏 action；不先承诺纯 JS 可覆盖 |
| 原生扩展 | Swift/WidgetKit/App Intents（v1.1） | 与主应用通过 App Group/明确协议共享最小数据 |
| 视觉 | RN 适配后的 `@tickcap/tokens` | iOS 18 用 Blur/渐变降级；降低透明度时使用实色 surface |

版本门禁：当前本机 Xcode 26.3 可用于 Expo SDK 55 风险样机；正式生产基线优先升级 Xcode 26.4+ 并锁定 Expo SDK 57。开工当天以 Expo 与 Apple 官方兼容表复核为准。

## 4. 账号体系（v1.1 候选；个人本地版不实现）

Web 需要账号保证跨浏览器可靠性；iOS 则必须允许未登录完成本地习惯闭环。MVP 采用“本地可用、登录后显式合并”的轻账号：

- **MVP：邮箱 + 验证码登录**（无密码，实现最简单、零短信成本）
- iOS 未登录数据写入本地 SQLite；登录时展示合并范围，成功前不清理本地副本
- 阶段二：**微信登录**（H5 内微信授权 + 小程序天然互通，两端账号打通是小程序阶段的前置条件）+ 手机号验证码
- 预留 `auth_identities` 表：一个用户可绑定多种登录方式，为多端互通铺路

## 5. 数据模型（核心 Schema）

所有表带四件套：`id (UUID)`、`created_at`、`updated_at`、`deleted_at (软删除)` ——这是未来 App 端离线同步协议的地基（UUID 客户端可生成、updated_at 做冲突比对、软删除可同步）。

```
users              用户（昵称、时区、日界、默认起床时间、会员状态）
auth_identities    登录方式（user_id, provider: email/wechat/phone, identifier）
tags               标签（user_id 为空=系统预置；emoji、颜色、父标签、排序、归档）
capsules           时间胶囊 ★核心表
                   (user_id, date, start_at, end_at, tag_ids[],
                    summary 一句话, detail 长文, mood 1-5, is_highlight,
                    source: manual/notification/backfill/calendar_draft,
                    is_private 敏感标记→永不参与 AI)
day_seals          日封存（user_id, date, sealed_at, note 手写感想, streak 快照）
ai_reports         AI 报告（user_id, type: daily/weekly/monthly/yearly,
                    period, template_id, content(md), user_edited_content,
                    model, token_cost）
templates          复盘模板（系统预置 + 用户自定义、口吻人设参数）
reminder_settings  提醒配置（间隔、生效时段、工作日/周末、暂停至）
events             埋点（匿名化，用于北极星指标看板）
```

设计要点：
- `capsules.date` 冗余存储"归属日"（凌晨 1 点的记录归昨天还是今天，由用户的"日界"设置决定，默认凌晨 4:00，精确规则见 [07 §2.1](07-详细技术设计.md)），所有按天查询走此字段，避免时区/跨天边界 bug——**这是此类产品最容易翻车的地方，schema 层面直接消灭**。
- `source` 字段区分记录来源，后续可分析"通知即记录"贡献了多少条，验证功能价值。
- AI 报告存两份：AI 原文 + 用户编辑版。编辑率是核心健康指标，且用户编辑不能被"重新生成"覆盖。

## 6. API 概览（REST）

> 本节仅为鸟瞰；完整契约（错误码、幂等、限流、注销、批量回填等）以 [07 §4](07-详细技术设计.md) 为准。

```
POST   /auth/email/code          发送验证码
POST   /auth/email/verify        登录/注册
POST   /sync/push                幂等上传本地 outbox
GET    /sync/pull?cursor=        增量拉取变更与 tombstone
GET    /capsules?date=           某日胶囊列表
POST   /capsules                 创建（客户端生成 UUID，支持幂等重试）
PATCH  /capsules/:id             编辑
DELETE /capsules/:id             软删除
GET    /tags · POST /tags · PATCH /tags/:id
POST   /days/:date/seal          封存（触发 AI 日复盘生成）
GET    /reports?type=&period=    报告列表/详情
POST   /reports/:id/regenerate   重新生成（换模板/人设）
GET    /reports/:id/stream       SSE 流式获取生成中的复盘
GET    /stats?range=             统计聚合
PUT    /reminder-settings        提醒配置
GET    /export                   全量导出（Markdown + JSON 打包）
```

## 7. 各端提醒能力的现实约束（诚实面对）

提醒是核心功能，但各端能力差异巨大，架构上用"**服务端统一调度 + 各端最优通道**"应对：

| 端 | 通道 | 现实约束 | 对策 |
|----|------|----------|------|
| Web H5 | Web Push | **iOS Safari 必须"添加到主屏幕"后才能收推送**；国内安卓浏览器支持参差 | 产品内做"添加到主屏"引导动画（本身也提升留存）；提醒能力弱是 Web 阶段已知短板，靠晚间封存单点提醒保底 |
| 微信小程序 | 订阅消息 | 一次授权一次推送，不能无限推 | 引导用户每天封存时顺手授权次日提醒；这是小程序排第二优先级的重要原因——**它补上 Web 的提醒短板** |
| iOS App | v1 本地通知；v1.1 APNs | 需要用户授权；后台/杀进程执行受系统生命周期约束 | 当前只做本地调度与幂等 action；远程调度不阻塞个人版 |

服务端只维护一份提醒调度逻辑（含智能节流规则），推送时按用户的活跃端选择通道——多端不是三个提醒系统，是一个大脑三张嘴。

## 8. 离线与同步策略（分阶段）

- **Web 阶段**：在线为主。写操作乐观更新 + 失败队列重试（IndexedDB 暂存），弱网下记录不丢；PWA 缓存让今日页离线可看。
- **iOS 个人本地版**：完全离线可用，SQLite 是唯一事实来源；业务表仍保留 UUID、时间戳、软删除和 outbox 形状，但当前不启动同步 runner。用户通过带版本和 SHA-256 校验的完整备份保存到“文件”或 iCloud Drive。
- **iOS v1.1**：启用 `/sync/push`、`/sync/pull` 增量同步；普通字段最后写入胜，`detail` 长文冲突保留双版本，删除以 tombstone 传播。
- **匿名转登录**：合并成功前保留本地副本；失败可重试，不静默覆盖云端或 Web 数据。

## 9. 安全与合规清单

- HTTPS 全程；验证码限流防轰炸；JWT 短时效 + 刷新令牌
- 敏感胶囊（`is_private`）在 AI 代理层硬性过滤，永不出现在大模型请求中
- 数据导出永久免费；Markdown/JSON 阅读导出与可恢复完整备份是两个独立入口
- 国内合规：ICP 备案（立即启动）、隐私政策 + 用户协议（上线前）、AI 能力仅调用已备案大模型 API
- 数据库每日自动备份，保留 30 天

## 10. 开发环境与工程规范

- pnpm workspaces + turborepo；TypeScript 严格模式全仓统一
- 提交规范 conventional commits；`core` 包单元测试必须覆盖时间推断/跨天归属/streak 计算（产品最容易出 bug 且最伤信任的三处逻辑）
- 环境：local（docker-compose 起 Postgres + Xcode Simulator/真机）→ staging/TestFlight → prod/App Store
- AI prompt 以版本化文件管理（`server/prompts/daily-v1.md`...），每次调优留档可回滚
