# 07 · 详细技术设计（开发实施规格）

> 本文是 [05-技术架构](05-技术架构.md) 的下钻实施规格：领域规则的精确定义、数据库 DDL、API 契约、前后端模块设计、测试与验收标准。**开发以本文为准；与 05 概览有出入处，以本文为准。**

## 1. 术语表（全项目统一用语）

| 术语 | 英文/代码名 | 定义 |
|------|------------|------|
| 胶囊 | Capsule | 一条时刻记录（时间段 + 标签 + 内容） |

| 默认起床时间 | wake default | 当天第一颗胶囊的默认开始时刻，默认 07:00 |

## 2. 领域规则规格（核心业务逻辑的唯一权威定义）

> 这些规则全部实现在 `@tickcap/core`，三端共享，必须 100% 单元测试覆盖。

### 2.1 归属日（date attribution）

- 用户设置**日界**（`day_boundary`，默认 04:00）。胶囊 `start_at` 换算到用户时区后，若时刻 < 日界，归属日 = 前一天；否则为当天。
- 例：日界 04:00，凌晨 01:30 记录的「夜宵」归属昨天的时间轴——符合人类心智（"昨晚"）。
- **修改日界不重算历史数据**，只影响之后的记录（避免历史时间轴突变）。
- 跨日界的胶囊（如睡眠 23:00–07:00）：归属日按 `start_at` 判定，允许 `end_at` 越过日界；当日时间轴尾部显示"→ 次日 07:00"截断样式。单颗胶囊时长上限 24h。

### 2.2 时间自动推断（infer times）

新胶囊默认时间段：

```
end_at   = now
start_at = 有同归属日的上一颗胶囊 ? 上一颗.end_at
         : max(now - 1h, 今日归属日的默认起床时间)
约束     = start_at 向下取整到分钟；若 start_at ≥ end_at 则 start_at = end_at - 1min
```

- 时长下限 1 分钟；手动调整步进默认 15 分钟（可设 5 分钟）。
- **重叠策略：允许重叠**（现实中"边吃饭边开会"存在，禁止重叠会造成编辑连锁反应）。服务端只校验 `end_at > start_at`；时间轴对重叠胶囊做横向缩进并列渲染。

### 2.3 空隙（gap）

按 `start_at` 排序的相邻胶囊之间，`next.start_at - prev.end_at ≥ 15min` 即渲染空隙区段（虚线，可长按补记）。最后一颗胶囊到"现在"之间同理。空隙是纯前端派生数据，不落库。

### 2.4 封存与 Streak

- 封存 = 对某归属日创建 `day_seal` 记录（触发 AI 日复盘生成）。已封存的日子可**解封**编辑，再次封存更新 `sealed_at`，streak 不受影响（以首封时刻为准）。
- **宽限规则**：D 日可在 D+1 的 12:00（用户时区）前封存并保持连续——晚上忘了、第二天早上补封不断签。
- Streak 计算：`streak(D) = 前一日在宽限内完成过封存 ? streak(D-1) + 1 : 1`，在封存时计算并快照到 `day_seals.streak`（避免历史回算）。
- 空轴不可封存（至少 1 颗胶囊），按钮置灰并提示。

### 2.5 敏感胶囊（is_private）

标记后：参与本地展示与统计**时长**，但其 `summary/detail` 在 AI 请求打包层被硬性剔除（见 [08 §2](08-AI复盘技术设计.md)）；导出时正常包含（数据是用户自己的）。

## 3. 数据库设计（PostgreSQL DDL 核心）

所有可同步业务实体表统一四件套：`id uuid pk default gen_random_uuid()`、`created_at`、`updated_at`、`deleted_at`（软删除，查询默认过滤）。认证、事件与同步基础设施表按各自幂等/游标主键设计。仅列业务字段：

```sql
users             (nickname, email unique, timezone text default 'Asia/Shanghai',
                   day_boundary_min int default 240,      -- 04:00
                   wake_default_min int default 420,      -- 07:00
                   time_step_min int default 15,
                   is_pro bool default false, pro_expires_at timestamptz)

auth_identities   (user_id fk, provider text check in ('email','wechat','phone'),
                   identifier text, unique(provider, identifier))

verification_codes(email, code_hash, expires_at, attempts int default 0)

refresh_tokens    (user_id fk, token_hash, expires_at, revoked_at)

tags              (user_id fk null,          -- null = 系统预置
                   name, emoji, color, parent_id fk null, sort int,
                   archived_at timestamptz)

capsules          (user_id fk, date date not null,        -- 归属日，冗余存储
                   start_at timestamptz, end_at timestamptz,
                   tag_ids uuid[] default '{}',            -- 主标签 = tag_ids[0]
                   summary text, detail text,
                   mood smallint check (mood between 1 and 5),
                   is_highlight bool default false, is_private bool default false,
                   status text default 'confirmed' check in ('draft','confirmed'),
                   source text check in ('manual','notification','backfill',
                                         'calendar_draft','onboarding'),
                   check (end_at > start_at),
                   check (end_at - start_at <= interval '24 hours'))
                   -- index: (user_id, date), gin(tag_ids)

day_seals         (user_id fk, date date, unique(user_id, date),
                   sealed_at timestamptz, first_sealed_at timestamptz,
                   note text,                              -- 手写"今日一句话"
                   streak int)                             -- 封存时快照

ai_reports        (user_id fk, type check in ('daily','weekly','monthly','yearly'),
                   period_start date, period_end date,
                   template_id fk, persona text,
                   content_md text, edited_md text,        -- AI 原文 与 用户编辑版分开存
                   model text, prompt_version text,
                   input_tokens int, output_tokens int,
                   status check in ('pending','streaming','done','failed'))
                   -- 同周期可多行（重新生成留历史），取 created_at 最新且 done 的为当前版

templates         (user_id fk null, kind, name, spec jsonb)  -- 结构 + 口吻参数

reminder_settings (user_id pk, interval_min int default 60,
                   active_from_min int default 480, active_to_min int default 1320,
                   weekday_mask int default 127, paused_until timestamptz,
                   seal_remind_min int default 1290,       -- 21:30
                   snooze_level int default 0)             -- 自动降频档位

push_subscriptions(user_id fk, device_id text, platform text check in ('web','ios'),
                   provider text check in ('web_push','apns','expo'),
                   token text, endpoint text, keys jsonb, environment text,
                   last_active_at timestamptz,
                   unique(user_id, device_id, provider))

events            (id bigserial, user_id null, anon_id, name, props jsonb, ts)

sync_operations    (op_id uuid pk, user_id fk, device_id text,
                   entity_type text, entity_id uuid, action text,
                   result jsonb, received_at timestamptz)
                   -- 客户端 outbox 幂等收据；同 op_id 重放直接返回原结果

sync_changes       (seq bigserial pk, user_id fk, entity_type text,
                   entity_id uuid, action text check in ('upsert','delete'),
                   changed_fields text[], payload jsonb, changed_at timestamptz)
                   -- index: (user_id, seq)；每次服务端写与业务表同事务追加
```

关键决策：
- `capsules.date` 冗余存归属日，所有按天查询走 `(user_id, date)` 索引——把时区/跨天判断锁死在写入时刻的 `core` 逻辑里，读取永不再算。
- `tag_ids` 用 `uuid[]` 而非关联表：标签数量少、永远整组读取、无需按标签 join 查胶囊以外的场景（按标签统计走 GIN 索引），省一张表和 N 次 join。
- AI 报告"原文/编辑版"分列，重新生成插新行——用户编辑永不被覆盖（产品红线）。
- `sync_operations` 只解决客户端 operation 幂等，`sync_changes.seq` 是每个用户增量拉取的逻辑游标；业务写入、operation 收据与 change log 必须同一数据库事务提交。

## 4. API 契约

通用约定：`Authorization: Bearer <JWT>`；请求体/响应体均为 JSON；时间一律 ISO 8601 UTC；分页用 `?cursor=&limit=`。

### 4.1 错误码

| HTTP | code | 含义 |
|------|------|------|
| 400 | `VALIDATION_FAILED` | 参数校验失败（附 `fields` 明细） |
| 401 | `TOKEN_EXPIRED` / `TOKEN_INVALID` | 前端触发静默刷新或登出 |
| 403 | `QUOTA_EXCEEDED` | AI 次数用尽（附 `quota` 信息，前端展示付费引导文案） |
| 404 | `NOT_FOUND` | |
| 409 | `ALREADY_EXISTS` | 幂等冲突（如重复封存），响应附既有资源 |
| 429 | `RATE_LIMITED` | 附 `retry_after` |
| 500 | `INTERNAL` | 前端统一"稍后再试"，写操作进离线重试队列 |

### 4.2 端点清单

```
# 认证
POST /auth/email/code        {email} → 204        限流：同邮箱 1次/分钟、5次/天
POST /auth/email/verify      {email, code} → {access_token, refresh_token, user}
                              码 6 位数字，10 分钟有效，错 5 次作废；哈希存储
POST /auth/refresh           {refresh_token} → 新 token 对（旋转式，旧 token 作废）
POST /auth/logout            → 204
DELETE /auth/account         → 204   注销：软删用户 + 7 天冷静期后物理清除（合规必须）

# 离线同步（认证后）
POST /sync/push
     {device_id, operations:[{
       op_id, entity_type, entity_id, action:'upsert'|'delete',
       base_updated_at?, client_updated_at, changed_fields[], payload
     }]}                                      ≤100 operations/次
     → {results:[{
          op_id, status:'accepted'|'conflict'|'rejected',
          entity?, conflict?, error?
        }], server_time}
     detail 冲突形状：
     {type:'field_conflict', field:'detail',
      local_value, server_value, server_updated_at}

GET  /sync/pull?cursor=<seq>&limit=500
     → {changes:[{seq, entity_type, entity_id, action, changed_fields,
                  payload, changed_at}],
        next_cursor, has_more, server_time}
     `seq` 在 JSON 中统一为十进制字符串，避免超过 JavaScript 安全整数；
     `next_cursor` 仍是不可解析、只可原样回传的不透明字符串。

同步规则：
- `op_id` 是 UUID v7；相同 `op_id` 重放必须返回同一结果，不能重复写业务表或 change log。
- `cursor` 是不透明的服务端序列；客户端仅持久化最后完整应用批次的 `next_cursor`。
- 新建资源由客户端生成 UUID v7；服务端用 `@tickcap/core` 重算 `capsules.date`。
- `base_updated_at` 与服务端当前版本一致时正常应用；不一致时比较 `changed_fields`。
- 非重叠字段可合并；同字段重叠采用服务端接收顺序的 last-write-wins，并返回合并后的权威实体。
- `detail` 同字段冲突禁止静默覆盖：返回 `conflict`，同时保留 local/server 两个版本；用户解决后用新 op 提交。
- delete 生成 tombstone 并进入 pull 流；所有已知设备越过其 seq 且超过保留期前不得物理清除。
- push 成功不代表本地可删：客户端必须先应用返回实体、提交本地事务，再删除对应 outbox。

# 胶囊
GET    /capsules?date=2026-07-27           → {capsules: [...]}
POST   /capsules             客户端生成 id（UUID v7），服务端按 id 幂等（断网重试不重复）
                              {id, start_at, end_at, tag_ids, summary?, detail?,
                               mood?, source, is_highlight?, is_private?}
                              → 201 {capsule}   （date 由服务端 core 计算）
PATCH  /capsules/:id         局部更新；改 start_at 会重算 date
DELETE /capsules/:id         软删除 → 204
POST   /capsules/batch       [{...}, ...] → 快速回填用，≤50 条/次（P1）

# 标签
GET /tags · POST /tags · PATCH /tags/:id（archived_at 归档，不物理删）

# 封存与报告
POST /days/:date/seal        {note?} → 201 {seal, report_id}    重复封存 → 409 + 既有 seal
DELETE /days/:date/seal      解封 → 204（streak 不变）
GET  /days?month=2026-07     月历数据：[{date, sealed, top_tag_color, capsule_count}]
GET  /reports?type=daily&cursor=
GET  /reports/:id
GET  /reports/:id/stream     SSE：event: delta {text} / done / failed
POST /reports/:id/edit       {edited_md}
POST /days/:date/report      重新生成（可换 template_id/persona）；限流 5 次/天/用户

# 其他
GET/PUT /reminder-settings
POST /push/subscriptions     {device_id, platform, provider, token?, endpoint?, keys?, environment}
DELETE /push/subscriptions/:device_id
GET  /export                 → 202 {job_id}；GET /export/:job_id → 打包下载 URL（zip: md+json）
GET  /stats?from=&to=        标签时长聚合、日均胶囊数（洞察页数据源）
POST /events                 埋点批量上报 [{name, props, ts}]，≤50 条/次
GET  /me · PATCH /me         （timezone/day_boundary/wake_default 等设置）
```

### 5.2 数据流与离线队列

- 服务端状态全部走 **TanStack Query**（key 约定：`['capsules', date]`、`['days', month]`、`['report', id]`）。
- **写操作乐观更新**：滴答 → 本地立即上轴（UUID v7 前端生成）→ 后台 POST；失败入 **离线队列**（IndexedDB，`idb` 库）：指数退避重试，恢复网络自动冲队；因 id 幂等，重试永不产生重复数据。队列中的胶囊在 UI 上带一个极小的"待同步"点，不打扰。
- 今日页数据 PWA 缓存最近快照，离线可看可记（记录进队列）。

### 5.3 关键组件规格

| 组件 | 要点 |
|------|------|
| `<Timeline>` | 虚拟化按需渲染（一天 ≤50 颗通常无需虚拟化，历史页月视图需要）；重叠胶囊横向缩进并列；空隙派生渲染；"现在线"每 30s 重算位置 |
| `<CapsuleCard>` | 果冻玻璃材质（tokens 驱动）；高度 = clamp(44, 时长映射, 120)；视口外停用 backdrop-filter（IntersectionObserver 切换 class） |
| `<TickBar>` | 玻璃岛；标签按使用频率排序（本地统计）；展开态为半屏弹层（Radix Dialog + 自定义样式） |
| `<SealFlow>` | 三幕流程组件；复盘 SSE 渐进渲染（`EventSource`）；封存动画 Motion 编排 |
| `<MonthCalendar>` | 档案馆月历；数据源 `GET /days` |

### 5.4 PWA 与提醒

- Web Push：VAPID；SW `push` 事件展示通知，`notificationclick` 深链到 `/today?focus=tickbar`。

### 5A.2 本地 SQLite schema

本地业务表字段与 03 的服务端实体语义一致，使用 snake_case；额外本地表如下：

```sql
local_meta        (key text primary key, value text)
                  -- schema_version / device_id / sync_cursor / last_sync_at
                  -- time_settings 保存 timezone/day_boundary_min/wake_default_min JSON

outbox            (op_id text primary key, entity_type text, entity_id text,
                  action text, base_updated_at text, client_updated_at text,
                  changed_fields_json text, payload_json text,
                  attempts int default 0, next_retry_at text, created_at text)

sync_conflicts    (id text primary key, entity_type text, entity_id text,
                  field text, local_value_json text, server_value_json text,
                  server_updated_at text, resolved_at text)

event_outbox      (id text primary key, name text, props_json text, ts text,
                  attempts int default 0)
```

约束：

- 使用 `PRAGMA journal_mode=WAL`、`foreign_keys=ON`；数据库初始化和每次 migration 均需事务。
- 创建/修改/删除业务实体与写入 outbox 必须在同一 SQLite 事务。
- UI 通过 repository 查询 SQLite；Zustand 仅保存筛选、弹层、草稿等短生命周期状态。
- 本地时间设置写入 `local_meta.time_settings`，进入今日页时重新读取；修改日界只影响之后新建胶囊，不批量重写历史 `date`。
- Onboarding 偏好写入 `local_meta.onboarding_preferences`，字段固定为 `completed/reminder_interval_min/seal_reminder_min`；已有 active capsule 的升级用户视为已完成，避免更新后再次被引导拦截。
- Onboarding 第一颗胶囊与 `record_done/onboarding_step` 必须在同一事务落库；从欢迎页到完成第一颗胶囊最多 2 次点击。引导末页只保存提醒偏好，不申请通知权限。
- 12 个系统预置标签在 `@tickcap/tokens` 中拥有稳定 UUID，SQLite 与未来服务端 seed 必须复用同一实体 ID；Web M1 的 `preset:key` 仅作为旧本地数据兼容 ID，不得进入新 API。
- 离线封存生成的规则复盘写入 `ai_reports`：`model='local'`、`prompt_version='local-v1'`、`status='done'`；解封不删除报告历史，重封插入新报告并保留首次封存时间与 streak 快照。
- 自定义标签最多 5 个，创建 tag 与 tag outbox 必须同事务；设置页返回今日页后应立即出现在快速滴答栏。
- 导出前必须提示文件包含用户正文与私密记录。Markdown/JSON 阅读导出只包含 active 内容，不承诺可恢复；完整备份是独立入口，通过系统分享面板交给用户保存到“文件”或 iCloud Drive。
- 个人本地版完整备份契约固定如下；`payload_sha256` 为 `payload` 经对象键排序、数组顺序不变的 canonical JSON 后计算的 lowercase SHA-256：

```json
{
  "kind": "tickcap-local-backup",
  "format_version": 1,
  "exported_at": "ISO-8601 UTC",
  "app_version": "0.1.0",
  "local_schema_version": 1,
  "payload": {
    "preferences": {
      "time_settings": {},
      "onboarding_preferences": {},
      "appearance_preferences": {}
    },
    "tables": {
      "tags": [],
      "capsules": [],
      "day_seals": [],
      "ai_reports": []
    }
  },
  "integrity": { "algorithm": "sha256", "payload_sha256": "64 lowercase hex" }
}
```

- 完整备份必须包含业务表的 active 与 soft-deleted 行以及三类本机偏好；必须排除 `device_id/sync_cursor/outbox/sync_conflicts/event_outbox`。外部备份输入还必须拒绝重复实体 UUID、重复封存日期、悬空标签 parent 和胶囊悬空 tag 引用。
- 恢复预检顺序固定为：文件大小/JSON → `kind/format_version` → Zod schema → `local_schema_version` 兼容性 → canonical payload SHA-256 → 本机合并预览；任一步失败均为零写入。
- 恢复按稳定 UUID 幂等合并：本机无该 UUID 时 insert；备份 `updated_at` 严格晚于本机时 replace；相同或更早时 skip。`day_seals.date` 若已由另一 UUID 占用，阻止整次导入，不静默替换。
- 用户确认后先在 App Documents 写入“导入前完整备份”，再在单个 SQLite exclusive transaction 内依次恢复 tags/capsules/day_seals/ai_reports 和三类偏好；任何写入失败全部回滚。恢复不导入也不重建 outbox/event_outbox，未来首次云合并按完整本地实体重新生成 operation。
- `local_meta.backup_status` 只记录本机可见性状态：最近生成完整备份时间、实体/删除状态数量、最近恢复时间与 7/14/30 天或关闭的 App 内提醒偏好；该运行状态不进入完整备份。系统分享返回只能证明文件已生成并交给系统，UI 必须写“最近生成”，不得误称已保存到 iCloud。
- 设置页在有业务数据且从未生成备份，或距最近生成时间达到提醒周期时，用中性文案提示；G4-L3 不申请通知权限、不创建系统通知。用户可关闭或切换 7/14/30 天频率。
- 导入前恢复点保存在 App Documents/recovery，按文件名中的 UTC 时间倒序展示数量并允许将最近一份交给系统分享；UI 必须说明它们仍在 App 沙盒中，卸载 App 后可能丢失，长期保障需另存到“文件”的 iCloud Drive 或“我的 iPhone”。
- `event_outbox` 事件名必须来自 09 闭集，属性只允许标量；正文属性名（summary/detail/content/content_md/edited_md/note/text）在共享 core 校验层物理拒绝。业务成功事件应与对应实体/outbox 同事务写入。
- schema migration 只前进且幂等；升级失败保留原数据库并阻止写入，禁止清库自愈。
- SQLite 文件依赖 iOS Data Protection；SQLCipher 需单独安全/恢复/性能评审后才能引入。

### 5A.3 同步状态机

```text
idle → pushing → pulling → applying → idle
          │          │         │
          └──────────┴─────────→ retry_wait
                                │
                         网络恢复/退避到期
```

1. App 启动、回前台、网络恢复、用户手动刷新触发 sync；同一时刻最多一个 runner。
2. push 按 `created_at, op_id` 顺序，每批 ≤100；逐项处理 accepted/conflict/rejected。
3. pull 循环到 `has_more=false`；每批 changes 与 `next_cursor` 在一个 SQLite 事务应用。
4. 进程中断后从最后已提交 cursor 继续；重复 change 按 `(entity_type, entity_id, updated_at/deleted_at)` 幂等应用。
5. `detail` 冲突写入 `sync_conflicts` 并保留本地草稿，界面使用中性文案提示选择；其他冲突使用服务端返回的权威实体。
6. 退避采用带抖动指数策略，最长 5 分钟；401 只允许一次 refresh 后重试，失败则暂停云同步但不影响本地记录。

### 5A.4 通知与深链

- 通知权限只在首次封存后的高光时刻或用户主动打开提醒设置时申请。
- URL scheme 使用 `tickcap://`；通知主体深链到 `tickcap://today?focus=tickbar`。
- 快捷标签 action 必须携带 `notification_id/action_id/tag_id`，生成确定性 operation key，重复回调不产生重复胶囊。
- 本地通知是离线兜底，APNs/Expo Push 是服务端调度通道；同一提醒实例使用共同 `notification_id` 去重。
- 前台、后台、系统回收、用户杀进程、锁屏五种状态必须在 G1/G5 真机矩阵验证；无法稳定覆盖的能力必须降级为“打开 App 并聚焦滴答栏”，不得虚报 0 秒完成。
- 个人本地版 G5-L 只创建一次性本地通知，不使用永久重复 trigger：App 启动/回前台、完成记录、封存/解封、时区/日界/起床/间隔/封存提醒变化后，取消 TickCap 自己保存的旧 identifier 并重算下一次间隔提醒和晚间封存提醒。不得调用“取消全部通知”误删其他模块或未来系统能力创建的通知。
- 间隔提醒基准取“当前时刻、最近有效胶囊 `end_at`、最近 App 打开时间”的最大值，再加用户选择的 30/60/120 分钟；候选点不在默认起床至晚间封存的活跃窗口时顺延到下一个可用窗口。这样刚记录或刚打开后，旧提醒会被取消且至少等待一个完整间隔。
- 晚间封存提醒按用户时区的 `seal_reminder_min` 生成；当前归属日没有有效胶囊、已经封存或提醒时刻已过时不安排，下一次在 App 打开或产生新记录后重新评估，不提前假设明天会有数据。系统时区或设置时区变化只通过上述 reconcile 重建，不在 UI/平台层复制时区换算。
- `local_meta.local_notification_status` 保存本机启用状态、iOS 权限结果、首次封存引导是否出现、最近打开/重建时间与两个已调度 identifier/fire_at；它是设备运行态，不进入完整备份。权限为 denied 后 App 不再次请求，只显示中性说明和系统设置入口。
- App 在下一次打开时若发现间隔提醒的 `fire_at` 已经过且没有对应点击/快捷 action/新记录，记为一次未回应；连续 3 次后 `snooze_level + 1`，实际间隔按 2 倍、4 倍递增且设置页中性展示“已自动放慢”。通知点击、新记录或用户重新选择间隔后清零；不得使用评判性文案。
- 通知 action 首版使用 `opensAppToForeground=true`：系统回收/用户杀进程后先启动 App，再处理 response。确定性 operation key 写入 `local_meta` 的 `notification_action:<key>`；该 key、胶囊、outbox 与 `record_done/reminder_click` 必须在同一 SQLite 独占事务提交，任一失败不留下半颗胶囊。

### 5A.5 iOS UI/性能与无障碍

- iOS 18 使用 BlurView/渐变实现果冻材质；降低透明度时切换实色 surface，减少动态效果时停用非必要弹性动画。
- 时间轴一天 ≤50 颗时优先使用简单稳定的原生列表；只有真实性能数据证明需要时才增加额外虚拟化依赖。
- `record_done.elapsed_ms` 与 `record_done.entry` 只用于本地 3 秒路径诊断；统计窗口默认取最近 30 次，禁止附带摘要、标签名等正文。
- Dynamic Type 不得截断正文操作；VoiceOver 顺序遵循“时间 → 标签 → 摘要 → 操作”。
- 交互热区至少 44×44pt；键盘、Safe Area、深浅模式均需真机验收。

## 6. 后端技术设计（apps/server）

### 6.1 模块划分（Hono）

```
src/
├── routes/        auth / sync / capsules / tags / seals / reports / reminders / export / events
├── services/      sync.service / capsule.service / seal.service / report.service / quota.service
├── ai/            provider适配器(deepseek|qwen|doubao) / prompt-builder / privacy-filter
├── jobs/          reminder.job（每分钟） / export.job / cleanup.job（注销冷静期清理）
├── core -> @tickcap/core   （归属日、推断、streak 等与前端共享）
└── middleware/    auth / rate-limit / request-id / error-handler
```

### 6.2 提醒调度（无 Redis 版）

`node-cron` 每分钟执行：查询"到点该提醒"的用户（SQL 直接算：当前时区时刻在 active 窗口内、距上次记录 ≥ interval_min × 0.6、距上次提醒 ≥ interval_min、未暂停、weekday 匹配）→ 逐个 Web Push → 写 `events(reminder_sent)`。未响应降频（`snooze_level`）在夜间任务统一评估。单实例即可支撑 10 万级用户，这条查询要有覆盖索引。

### 6.3 AI 生成流水线

封存 → `ai_reports` 插入 `pending` 行 → 进程内队列（并发 2，p-queue）→ privacy-filter 剔除敏感胶囊内容 → prompt-builder 组装 → 供应商流式调用 → 边生成边写缓冲 + 推给 SSE 订阅者 → `done`。失败重试 2 次后置 `failed`，前端提供"重试"按钮。详见 [08](08-AI复盘技术设计.md)。

### 6.4 安全清单

- 全局限流（IP + 用户双维度）；验证码接口独立更严限流
- JWT：access 2h / refresh 30d 旋转；refresh 哈希落库可吊销
- 输入校验统一 zod schema（与前端共享自 `@tickcap/api`）
- SQL 全走 Drizzle 参数化；detail 字段渲染前 sanitize（防存储型 XSS）
- 导出/注销等敏感操作二次确认 + 操作日志

### 7.2 MVP 功能验收标准（抽核心）

| 功能 | 验收标准 |
|------|----------|
| 滴答记录 | 冷启动 → 完成一颗胶囊 ≤3 次交互；断网滴答，恢复后自动同步且不重复 |

## 8. 环境与发布

- 环境：local（docker-compose: pg + server + web + iOS Simulator/真机）→ staging + TestFlight → prod + App Store
- CI（GitHub Actions）：lint + typecheck + 单测 + API/同步集成测试 + iOS 可重复 prebuild；服务端 staging 自动部署，TestFlight/prod 手动确认
- 数据库迁移：drizzle-kit 生成 SQL 迁移文件入库，禁止手改线上 schema

- 监控：服务端结构化日志 + 错误上报（Sentry 自托管或轻量替代）；`ai_reports` 成本日报（token 用量 × 单价）自动入群/邮件
